# Strategic Survival Engine

> **Кросс-языковая экосистема для симуляции выживания в пост-апокалипсисе.**
> Мир — это данные. Картинка — это проекция. Наблюдатель — точка зрения.

---

## 🎯 Философия проекта

Это не «игра». Это **мир**, который **описывается** и **проявляется** тогда, когда есть наблюдатель.

Три принципа:

1. **Мир существует как 0 и 1.** Не как картинка. Как **данные**.
2. **Картинка рождается в момент восприятия.** Ушёл наблюдатель — картинка исчезла, данные остались.
3. **Наблюдатель ≠ игрок.** Наблюдатель — точка зрения. Игрок — тело в мире.

**Что это даёт:**
- Мир может быть **огромным** без нагрузки на память.
- **Детерминизм:** один seed = один мир всегда.
- **Расширяемость:** новый объект = новый файл данных, а не правка движка.

---

## 🎮 Что это за игра

**Зомби-апокалипсис.** Катастрофа уничтожила 95% человечества. Остались только иммунные — и они тоже гибнут от зомби. Рождаются новые герои, появляются в одном из **6 городов** и начинают своё путешествие.

**Жанр:** топ-даун симуляция выживания.
**Вид:** сверху, без 3D. Стилизация под классические top-down RPG.
**Фокус:** тактика, ориентация, выживание, а не графика.

## 🧠 Ключевые идеи

### 1. Шар как замкнутый мир

Мир — это **замкнутая сфера**. Уйдя за правый край — появляешься слева. Уйдя вверх — появляешься снизу.
WORLD_SIZE = 3072 px
Обзор = 760 px (радиус 380 × 2)
Отношение = 4.04× — шар в 4 раза больше области зрения

text

Математика: `wrapDelta(d)` возвращает **кратчайший путь** на шаре. Это позволяет всем объектам знать, где находится наблюдатель — без ухищрений.

### 2. Стриминг ячеек

Мир **не хранится целиком**. Хранится только то, что **близко к наблюдателю**.
R_LOAD = 800 px — граница загрузки
R_FADE = 420 px — граница затухания
R_CORE = 40 px — зона полной чёткости

В ячейке 64×64 px:

Ячейки ближе R_LOAD — загружены

Дальше R_LOAD × 1.4 — освобождаются

text

### 3. Кэш ячеек

Каждая ячейка генерируется **один раз**, рисуется **один раз** в свой буфер. При повторном попадании в зону — **берётся из кэша**.

Хранится не буфер 64×64 (4096 пикселей), а **список активных пикселей** (~500). Это даёт 5–10× ускорение.

### 4. Размытие зрения

**Размытие — свойство наблюдателя, а не мира.** Оно построено в **экранных координатах**, привязано к центру экрана. Наблюдатель всегда в центре → маска всегда «в глазах», а не «в мире».

Используется гауссова кривая:
a = exp(-(d - R_CORE)² / 2σ²)
σ = (R_FADE - R_CORE) / 2.5

text

### 5. Прямая растеризация

Никаких `std::vector<Pixel>` внутри hot loop. Всё рисуется **прямо в буфер** через:
- Брезенхэм для линий
- `std::fill` для фона (одна инструкция)
- Блит ячейки — копия списка активных пикселей

💡 Ключевые решения
Почему C++, а не C#?
Ядро должно работать без GC-пауз. C# — для высокоуровневой логики.

Почему Win32, а не SDL/OpenGL?
Минимум зависимостей — ноль сторонних библиотек.

Работает везде, где Windows.

Позже можно добавить SDL как альтернативную платформу — не переписывая мир.

Почему программный рендер, а не шейдеры?
Детерминизм — одинаковый результат на всех машинах.

Работает без GPU — на слабом железе.

Меньше кода — 100 строк вместо 5000 строк шейдеров.

Почему данные отдельно от кода?
Изменение травы не должно требовать пересборки движка. Один JSON — и другой биом.
